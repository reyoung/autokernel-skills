# 构造测试基线

将用户的优化目标转为可复现、可审查的测试基线，包含两个独立入口：

- **benchmark**：测量需要优化的 metric，输出数值、单位和统计口径。
- **verify**：测量用户指定的约束指标，按阈值或断言判定实现是否有效，防止 code agent 通过破坏语义、缩减工作量等方式获得虚假的优化收益。

verify 是 benchmark 结果有效的前提。高分不能抵消 verify 失败；多项约束不能通过平均值掩盖单项失败。本任务交付测试及初始结果，优化实现属于后续任务。

## 1. 明确用户指定的指标

先阅读项目约定、待优化入口、现有测试和参考实现，复用已有运行方式。用户必须指定要生成的 **benchmark metrics** 和 **verify metrics**；已有对话中的明确指定同样有效。

任一类缺失时，集中询问缺失项，可以根据代码提出候选指标供用户选择，但不能自行把建议当作用户要求。等待期间可继续检查代码和环境，指标明确后再实现依赖这些选择的脚本。

为每项指标整理以下约定，沿用用户要求和现有项目定义：

| 类别 | 必须明确的内容 |
| --- | --- |
| 公共范围 | 被测入口、输入分布或数据集、规模、适用环境，以及哪些代码允许优化 |
| benchmark | 指标名称、含义、单位、优化方向、测量边界、重复次数和聚合方式 |
| verify | 指标或不变量、独立的期望值来源、通过阈值、覆盖用例、失败条件 |

verify metrics 可以是误差、成功率等数值，也可以是输出形状、输入未被修改等布尔断言。影响正确性或排名的歧义（例如容差、是否包含数据传输、多指标权重）需要用户明确；普通实现细节可采用项目惯例并记录。保留多项 benchmark 的独立结果，只有用户定义了组合规则时才计算总分。

完成条件：两类指标均有用户来源，且每项指标可以转为实际测量或明确判定。

## 2. 构造 verify

先把有效实现的边界变成可执行检查，再测量性能：

- 从可信参考实现、已知答案、数学性质或独立计算建立 oracle。被测实现自己的输出、日志或成功标志不能作为正确性的唯一依据；参考实现不能转调候选实现。
- 按用户指标覆盖正常、边界和容易投机的输入。适用时加入随机输入、不同规模和重复调用，检查硬编码结果、漏算、状态污染或仅支持样例等行为。随机种子应可记录和复现。
- 数值检查明确容差及比较公式，按语义处理 NaN、Inf、空输出、形状和类型。不能只比较可能掩盖局部错误的平均值。
- 让每个失败报告具体指标、用例、实际值和期望值。断言失败、异常、超时、缺失结果或必需用例被跳过均不得计为通过；verify 失败时返回非零退出码。

将评测脚本、参考答案、阈值和数据定义与可优化代码划清边界。基线完成后记录其版本或内容摘要；如评测定义发生变化，应建立新基线并重测。摘要只有与可信记录比较才有意义。如果 agent 能修改评测环境中的所有文件，本地 verify 无法单独保证防作弊；记录实际边界，必要时采用由外部评测方控制的只读评测或隐藏用例。不要把保存在同一可写工作区的文件声称为隐藏测试。

完成条件：每项 verify metric 有对应检查和可信判定来源，失败会阻止结果被认定为有效。

## 3. 构造 benchmark

benchmark 调用真实被测入口，测量用户要求的完整工作量。测量输入和 verify 的适用范围一致；用于验证和计分的候选代码及其配置必须一致。

- 按指标定义划定计时、内存或其他计数边界，明确初始化、编译、预热、I/O 和数据传输是否计入。需要区分冷启动和稳态时分别报告。
- 对异步执行使用适合运行时的同步或事件测量，确保测到的是工作完成时间。保证结果被实际计算和使用，避免空调用或优化器消除工作。
- 由评测脚本独立计时或计数，不能直接信任候选实现自报的耗时、吞吐或分数。吞吐量的工作量来自实际完成并满足约束的任务。
- 记录重复测量的原始值和约定的汇总值，按需要报告波动。固定比较所需的硬件、依赖、输入、并发和运行设置；记录无法固定的差异。
- 提供独立 benchmark 入口以便调试，并提供明确的完整评测命令或流程：verify 通过后才将 benchmark 纳入有效基线。单独执行的测量结果标明验证状态，verify 失败或未运行时不得标记为有效得分。

完成条件：所有 benchmark metrics 均能从真实执行中得到，且测量口径足以支持后续公平比较。

## 4. 验证测试本身并记录基线

在当前实现上运行 verify 和 benchmark，并对 verify 做有针对性的反例验证：

- 用可信实现或已知正确样例确认合法行为可通过。若当前实现不满足约束，保留失败证据，不通过放宽阈值来制造有效基线。
- 在隔离的临时副本或测试替身上，选择与实际风险对应的错误实现，例如返回固定值、篡改部分结果或省略部分工作，确认 verify 会拒绝。为每项 verify 指标准备能触发其失败条件的反例；不必穷举无关攻击。
- 确认失败状态能传递到完整评测结果，而不只是打印错误后仍返回成功。完成后清理测试替身，保留可复现反例的方法。

保存基线结果，至少包括实现和评测的版本标识、环境、数据与随机种子、执行命令、benchmark 原始值及汇总、verify 各项实际值与通过状态。速度提升等相对指标必须关联采用同一口径的参考测量。

运行环境、数据或依赖不足时，明确记录未执行项和具体阻碍；可以交付已完成的脚本，但不能编造测量值或声称基线已验证。

## 交付

遵循项目语言和目录惯例，交付 benchmark、verify 两个入口及其必要的数据或配置，以及一份简短的基线说明与结果文件。说明应让下一位使用者能找到指标定义、运行命令、通过条件、可优化范围和反例验证结果。

结束时列出生成的文件、用户指定的两类指标、实际运行结果与尚未完成的验证。只有全部必需检查通过且测量完成，才称为已建立有效基线。
